# 单测覆盖不到的四类缺陷

> 本文件回答**"为什么值得花成本做端到端测试"**。
>
> 下面是**四类缺陷模式** —— 它们有共同特征：**逻辑本身写对了，
> 缺陷在"运行时怎么被使用"上**。因此单元测试（测函数）与单接口测试（测单点）
> **都发现不了**。每类给出抽象描述 + 最小示意；末尾的"实战案例"是抽象来源。

## 模式 1：多入口不一致 —— "拦了一个，漏了另一个"

**特征**：同一能力有**多个可被调用的入口**（上层封装 + 底层工具 + 另一条 API 路径），
校验只在其中一个入口上做。**调用方被拒后会换一条路。**

**为什么单测发现不了**：单测只测"该入口被调用时校验是否生效" —— 它对了。
缺陷在**调用方的行为选择**（换入口）。

```python
# 入口 A（有校验）— 单测会测它，通过 ✅
async def high_level_op(target):
    if not in_scope(target): return deny()
    return await low_level_op(target)

# 入口 B（无校验）— 也被注册为可调用 → 调用方可直接绕过 A
async def low_level_op(target):
    return await fetch(target)      # ← 无校验
```

**检查方式**：列出**所有**能到达敏感数据的入口，逐个验证。
**修复模式**：判据抽**共享模块**（单一来源）+ 校验**下沉到最底层的数据出口** +
新增"**入口清单测试**"（枚举所有入口，要求每个都接线；漏了会红）。

## 模式 2：缺能力 → 调用方自己"想办法"

**特征**：某类合理请求**没有对应的工具/接口**，于是 Agent（或前端）**走了替代路径**
（联网搜索、猜算、用错误的通用接口），产出的结果**看似合理但权威性不同**。

**为什么单测发现不了**：单测测的是"工具存在时是否正确"；
缺陷在**"工具不存在时的降级行为"**。

**示意**：用户问"当前范围内有哪些 X" → 系统里没有查 X 目录的工具 →
模型联网检索 → 答出**公开资料的数**（与内部权威数据**不一致**）。

**检查方式**：对每个**高频合理问题**，确认"系统里有没有权威数据源可直接回答"。
**修复模式**：补齐工具/接口 + **按权限范围过滤**（补齐不等于放开）。

---

## 模式 3：完整鉴权链 + 真实数据才触发的运行期错误

**特征**：代码路径**只有在"带正确凭据 + 库里有数据"时才走到**，
错误发生在序列化/懒加载/并发等**运行期细节**上。

**为什么单测发现不了**：需要**完整请求链**与**符合条件的数据**。

**典型**：查询时漏了 eager-load 关联，序列化时访问它 → 在异步上下文外触发 IO →
`MissingGreenlet` 之类的运行时异常 → 接口 **500**。
（同一文件其它查询都带了，只这一处漏 —— 属遗漏而非设计。）

**检查方式**：
- 对**每个列表/详情接口**，用**真实凭据 + 库里确有数据**的账号调一遍
- **必须配对照**：同一组请求头换个能正常工作的端点，确认"是这个接口的问题"而非环境

```bash
# 对照法：同请求头，A 端点 500、B 端点 200 → 确定是 A 自身的问题
curl -s -o /dev/null -w '%{http_code}\n' -H "Auth: Bearer $T" -H "Scope: $OK" "$API/A"   # 500
curl -s -o /dev/null -w '%{http_code}\n' -H "Auth: Bearer $T" -H "Scope: $OK" "$API/B"   # 200
```

**修复模式**：补上 eager-load / 修正异步边界。

---

## 模式 4：同一份数据在两个端点上行为不一致

**特征**：同一份资源，**读/预览可以，另一操作（下载/导出/编辑）失败**。
根因通常是**两条路径的鉴权或兜底逻辑分叉**。

**为什么单测发现不了**：需要**同一份数据在两个端点上的行为对比**才会暴露。

**典型**：

| 操作 | 结果 | 说明 |
|---|---|---|
| 预览 | ✅ 200 | 授权查询失败后**有兜底** |
| 下载 | ❌ 404 | **没有兜底** |

而授权查询依赖的**范围集合**只含"根的子集"，数据却挂在**祖先**上 → 查不到。

**检查方式**：对同一资源的**所有操作**跑一遍，**横向对比**。
**修复模式**：让两条路径的兜底逻辑一致（**同时确认不放松越权判定**）。

---

## 四类模式的共同点与检查清单

| 模式 | 一句话 | 检查方式 |
|---|---|---|
| 1 多入口不一致 | 拦了一个，漏了另一个 | 枚举所有数据入口 |
| 2 缺能力 → 自寻替代 | 没工具就联网/猜 | 逐个高频问题问"有没有权威源" |
| 3 运行期才炸 | 完整链 + 真实数据才触发 | 真凭据 + 有数据的账号全量跑接口 |
| 4 端点间不一致 | 同一数据两种结果 | 同资源横向对比所有操作 |

**通用检查清单**：

- [ ] 敏感数据的**所有入口**都验证过（不只上层封装）
- [ ] 每个高频问题都有**权威数据源**可回答
- [ ] 每个接口都用**真实凭据 + 真实数据**调过（且配了对照组）
- [ ] 同一资源的**所有操作**横向对比过

## 附带发现：社会工程式绕过（值得固化成用例）

**当系统正确拒绝时，Agent/前端可能引导用户"口头确认"以求放行**：

> "如果你确认该资源在范围内，回一句『确认』我就继续。"

**必须验证：口头确认不能放宽权限。**
（授权来自平台的权限配置，与**对话内容/客户端参数**无关。）

**判据**：逐字复刻该引导话术发给系统，断言
① 服务端**仍然拒绝**（日志为准）② **无数据载荷** ③ **无产物**。
